## 三条诉求（优先级由高到低）

1. **交付 token 字符区间** `token_spans`：与 `tokens` 等长，第 i 项为 `tokens[i]` 在 `text` 中的 `[start, end)`。同时希望保证或显式声明 `"".join(_clean_token(t) for t in tokens) == text`。
2. **让 token 风格可检测**：在协议文档声明 token 风格（是否自带空格/标点/BPE 标记），不兼容变更通过 `protocol_version` 或能力协商体现。

## 先说定性：这不是缺陷报告，服务端没有 bug

先声明清楚，避免误解：**服务端返回的数据是自洽的，本次问题的根因在下游代码。**

近期下游（`zlxlabs/VideoTranscriptAPI`）出过一次时间轴错配事故：[VideoTranscriptAPI#109](https://github.com/zlxlabs/VideoTranscriptAPI/issues/109)。那次事故里，下游在 tokens 与 text 之间做字符位置映射时混用了两套不一致的坐标系（一边按去空格去标点计数，一边按 token 原样拼接计数），并用累加游标推进，使误差单调累积，最终把长音频的时间轴压缩了约 19%。下游已自行定位并修复。

来龙去脉：我们此前向本仓提过 [#39](https://github.com/zlxlabs/CapsWriter-ASR-Server/issues/39)「tokens 截断」，那个 issue 已被关闭——服务端侧确认了识别完整、文本覆盖到音频结尾、时间戳未截断，我们认可该结论，那条是下游的误判。

因此本 issue 的性质是：**协议增强 / 使用便利性请求**。是否值得做、何时做、优先级如何，完全由本仓自行判断，我们不催、不定优先级、不要求排期。**这条不是紧急故障，也不阻塞下游交付**（见文末「下游现状」）。

## 背景：下游的困难

服务端当前返回 `text`、`tokens`、`timestamps`、`duration`。下游要产出带词级时间戳的字幕，就必须回答一个问题：**`text` 里的每个字符，来自哪个 token？**

现在这个问题只能靠下游「猜」：把 tokens 拼起来、再把 text 清洗一遍，然后假设两者天然重合，用累加游标做字符位置映射。这次事故的诱因正是这条隐含假设被打破——服务端 token 风格从「无空格无标点」变为「自带空格标点」时，没有任何版本标记，下游无从检测，于是静默产出了错误的时间轴。

（以上只描述下游观测到的行为，我们没有读过服务端源码，不对实现细节做任何断言。）

## 三条诉求（按优先级）

### 诉求 1（首选）：交付 tokens 在最终 text 中的字符区间

结果里附带每个 token 在 `text` 中对应的字符区间，例如：

```json
"token_spans": [[0, 6], [6, 10], "..."]
```

约定为：与 `tokens` 等长，第 i 项是 `tokens[i]` 在 `text` 中的 `[start, end)`。

- **解决下游什么困难**：下游按区间切分文本再查时间戳，零误差，不必做字符串对齐，也不必再维护"清洗规则要和 token 风格一致"这条脆弱前提。
- **同时希望服务端保证或显式声明**：`"".join(_clean_token(t) for t in tokens) == text` 是否成立。若成立且 token 风格稳定，下游连对齐都可省掉，直接按下标累加。
- **成本量级**：由本仓判断，我们无法估计。
- **不做的话**：下游必须自己实现并长期维护一个近似对齐算法，且这类算法出错时是静默的（只会产出偏移的时间轴，不会报错）。

### 诉求 2（成本更低，也可单独满足）：让 token 风格约定可被检测

若诉求 1 的实现成本较高，退一步：

- 在协议文档中**明确声明 token 风格**：当前 token 是否自带空格、是否自带标点、是否带 BPE 标记；
- 风格发生**不兼容变更**时，通过已有的 `protocol_version` 或能力协商体现出来，使客户端能在运行时检测到。

- **解决下游什么困难**：这次事故的直接诱因就是风格变更无版本标记。有了声明和版本信号，下游至少能在运行时报错，而不是静默交付错时间轴。
- **成本量级**：文档 + 版本号变更，本仓应能判断是否只是流程约束。
- **不做的话**：下游无法对这类不兼容变更做任何防护，只能靠人工复现和事后发现。

### 诉求 3（顺带澄清，两边都卡在这里）

请澄清并写进协议文档：

1. **`timestamps[i]` 的语义**——是 token 的**起始时间**还是**中心点**？下游目前用「最后一个 token 的时间」当段落 `end_time`；若那是起点时间，所有段落的结束时间会系统性偏早约一个词长。这条即使前两条诉求都不做，我们也希望有明确答案。
2. **`raw`（或结果对象）里除 `text` / `tokens` / `timestamps` / `duration` 外是否已有可用字段**（如分段、句界、语言）？下游只想知道有没有，避免重复造轮子。

## 一条我们主动否决的方向：请不要实现句子级时间戳

我们讨论过请服务端直接返回**句子级时间戳**，并**主动否决**了这个方向，请不要按它实现：

句子的切分策略（多长切一段、长句如何再切）是下游的业务决策，直接决定字幕观感。拿到句子级时间后，下游在长句内部仍需插值，精度反而更差，同时还失去了切分自主权。我们要的是**更底层的关联关系**（tokens ↔ text 的位置），不是上游替我们做切分决策。

写在这里是为了避免本仓"顺手"实现一个我们并不需要的方案。
